# Nodus Support

Independent Electron + React support application in the Nodus repository. Its S mark uses the Nodus node style and `#C7C21C`; the main Nodus N mark is unchanged. SVG geometry lives in `shared/support/mark.svg`; `node scripts/generate-support-icons.mjs` produces PNG, ICO and ICNS assets for every platform.

## Current delivery and safety gate

This implementation is **not yet qualified for public repair use**. Inspection, direct log reading, verified protection, retained sessions, isolated diagnostic workers and reviewed reports are implemented. The interface explicitly displays this state. `qualified-repairs.json` is deliberately empty: opening the full Nodus application on a copied profile, activating solutions, restoring archives and reinstalling are blocked in the main process until their native safety matrix passes. The recovery-artifact publisher enforces the same gate. The independent diagnostic app can be published with repairs disabled.

Do not fill that catalog merely to produce installers. Unknown problems must produce a report. In particular, this release does not certify repairs for AI providers, model downloads, synchronization, individual tools, drivers, antivirus or operating-system components. The runtime worker's canvas check proves that Electron can start and draw; it does **not** prove the normal Nodus application or an affected tool works.

## Development

Use the repository lockfile and Node 22:

```sh
npm ci
npm run support:dev
npm run support:typecheck
npm run support:test
NODUS_SUPPORT_LARGE_FILES=1 npm run support:test
node scripts/verify-nodus-support-ui.mjs
node scripts/verify-nodus-support-flow.mjs
node scripts/build-nodus-support.mjs --runtime
node scripts/verify-nodus-support-runtime.mjs
npm run support:dist
```

The large-file environment assignment above is POSIX syntax; on PowerShell use `$env:NODUS_SUPPORT_LARGE_FILES = '1'`. The native early-bootstrap check additionally requires a current `npx vite build`, then `node scripts/verify-nodus-support-protocol.mjs`.

`support:build` bundles a separate main process, preload and UI in `build/support-app`. It imports no normal Nodus bootstrap, database, provider or engine. Electron is the same version as Nodus but has its own executable and runtime. Production Node dependencies are excluded from this package because its few JavaScript dependencies are bundled. `verify-nodus-support-runtime.mjs` checks the actual ASAR and launches the packaged executable against a synthetic profile.

The guided mode presents one proposed check at a time, with more checks available on demand. Stopping an automatic sequence also prevents the next check from starting if the current one has just finished. Reinstallation exposes a copied-data trial and validates the resulting installed package (or the signed artifact hash for AppImage) before asking whether it works; confirmation does not redirect the main application to that test profile. A trial cannot be opened with a different runtime version. Archive restoration exposes real byte progress from the isolated worker and displays the source archive and its recorded date. Bundled dependency notices are derived from the actual esbuild inputs; standalone packages include Electron/Chromium notices.

`support:dist` creates Windows x64 NSIS and portable executables, macOS arm64 or x64 DMG/ZIP, and Linux x64 AppImage/DEB/RPM on the corresponding native build host. **Support is not bundled in the normal Nodus installer.** `build/supportRuntime.cjs` writes only the small early-bootstrap protocol and ASAR hash; it does not compile or copy Support. Installing/updating Nodus does not install Support automatically.

Settings → Help → Nodus Support finds the latest published Support in the current stable/beta channel, validates a pinned Ed25519 manifest, then offers a separate managed installation in the user account. OS and the architecture of the running Nodus select the independent runtime. No administrator rights are needed for this route. The full extracted contents are bound to the signed manifest, rechecked before opening, and checked with native signatures where supported. A new version gets a separate persistent directory and system application entry. Earlier versions and interrupted downloads are retained; a damaged update does not replace an older verified copy. Once installed, Support opens offline. Nodus waits for a ready receipt before its cooperative quit/save guards run.

A separate “Save system installer” option detects the current Nodus format (Windows NSIS, macOS DMG, Linux AppImage, DEB or RPM) and downloads that native installer after confirmation. It saves into a new folder, verifies it, and shows it for the user to run with the OS installer. It does not execute a privileged installer automatically. Downloading/installing/updating Support is distinct from the helper’s repair/reinstall/update of **main Nodus**. If main Nodus cannot open, the same independent assets can be downloaded manually from GitHub Releases.

`.github/workflows/release-build.yml` dispatches `release-support.yml` **after `verify-and-publish` succeeds**. This separate run validates that the tag is already public, runs the four-platform safety workflow, builds/signs/notarizes Support, and appends its assets to that existing release. `GITHUB_TOKEN` release events do not start chained workflows, so the dispatch is explicit. Nothing compiles Support in the normal release jobs or Intel append job; no Support result is a prerequisite of normal publication. The signed Support manifest is uploaded last, after its downloads exist. The UI shows that Support is still being prepared while those assets are absent, and retains access to an already installed copy. A failed Support run can be retried without republishing Nodus.

`support-app-release.mjs` publishes the diagnostic app with its repair gates intact. Only after qualification does the post-publication workflow reconstruct the already published Nodus installers (without rebuilding or changing them) and publish signed recovery runtimes via `support-release.mjs`. Active diagnostics use protocol 1. Older or damaged installations can prepare a separate, signed-manifest-verified compatible runtime with user confirmation. A newer diagnostic runtime cannot activate a recovery selection for an older or incompatible installation.

## Data boundary

- Sources are opened for reading by the assistant. It never opens original SQLite files through SQLite. The inventory includes the profile, registered external vault files and their WAL/SHM files, and the configured global library. Encrypted credential blobs are copied as bytes, never put in a report.
- Invalid preferences, missing registered sources, links/junctions, locked files, insufficient space, running Nodus or overlapping source/protection locations stop protection. Unrecognized external storage layouts are not certified for interactive repair.
- Every protection has a SHA-256 manifest, byte counts, private permissions and verification of the complete file set. Protection uses persistent storage separate from the source profile. It reserves space for protection, trials and recovery; it never prunes older sessions.
- The worker receives a new profile or verified copy. Registered external vault paths and the global library path are remapped into that profile, including adjacent WAL/SHM files. No normal application import occurs in the early worker bootstrap. Network requests in its renderer are denied.
- Damaged Support history remains on disk and is reported. An unreadable active selection leaves the independent assistant usable for inspection and report preparation, while blocking file-changing checks until the user explicitly selects a profile.
- Journals use fsynced prepared records and exclusive hard links. Interrupted prepared records are retained, and incomplete records cannot become committed transitions. A damaged committed journal fails closed. No failed trial, partial copy or previous state is removed automatically.
- Original files must still match their verified inventory before selecting a recovered workspace. Fresh empty diagnostic profiles cannot become the main profile. Undo detects new work in a recovery workspace and offers keeping that workspace or selecting the previous one after creating and verifying another copy of the recent edits. Successive recovery selections resolve to the latest workspace; undo must follow reverse order. Both versions remain available.
- Binary replacement stages and preserves the old installation; it never runs an uninstall first. macOS bundle renames and AppImage replacements are journaled. Rollback retains the attempted installation. Privileged package-manager installation and Windows NSIS recovery still need native failure-injection tests before qualification.

Support uses a deliberately limited IPC API with sender validation, context isolation, sandboxed UI, a local custom protocol, restrictive CSP, no shell-command API and no general filesystem API. See [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security).

## Reports and privacy

Existing logs are read directly; the Nodus retention module is never initialized. The default is 50 errors, with 20, 100, all available errors and date filters. Real pipeline badges, HTTP statuses, repeat counts and nearby technical events are preserved without message parameters or document/job identifiers. Long Markdown previews show at most 100 errors; the saved structured report retains the complete selection. Parsing is bounded to 32 MiB per log; complete originals remain available through the separate local export.

Recommended ZIPs contain reviewed English Markdown, allowlisted technical diagnostics, classified errors and a manifest of the exported files. They omit documents, databases, credentials, paths and arbitrary log messages. Error names outside the known catalog become `UNCLASSIFIED_ERROR`. The user can edit the Markdown and must review it before copying, exporting or opening an issue. Automatic filtering is not a promise of anonymity, especially after manual edits.

Worker outcomes have unique request IDs and private durable result files, so Windows GUI startup does not depend on stdout being attached or flushed. Bounded worker stderr remains in separately marked private local logs; it never enters classified reports. Original and private worker logs require a separate native confirmation and export. They are never attached to GitHub automatically. Issue creation uses the existing bug form and [GitHub URL parameters](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue), caps the encoded URL at 2,000 characters, and uses a short summary plus a reviewed clipboard copy when needed. The user submits the issue and attaches files in their browser. No GitHub authentication is stored.

## Release setup and remaining qualification

`trusted-release-keys.json` pins the dedicated Ed25519 manifest key `nodus-support-2026-01`. The corresponding repository secrets `NODUS_SUPPORT_RELEASE_PRIVATE_KEY` and `NODUS_SUPPORT_RELEASE_KEY_ID` have been configured. The private recovery copy is outside Git, under `~/.config/nodus-release-signing/support-manifests-2026/`, with private permissions. It is never printed or bundled. The existing macOS code-signing certificate remains separate and unchanged. Future keys can be generated with `npm run support:keygen -- <key-id> <private-folder-outside-git>`; `scripts/configure-support-signing.mjs` performs initial GitHub setup and refuses to overwrite existing signing secrets. Signed manifests bind the exact version, OS, architecture, runtime, installer sizes and SHA-256 hashes. Missing trust, bad signatures, modified downloads and wrong architecture fail closed. Candidate native signatures are checked before execution where supported. Every artifact declares its platform-signature policy in the signed manifest: a Windows build with no publisher certificate is accepted only when explicitly declared unsigned; invalid, modified or untrusted signatures are always rejected. Windows displays an additional explanation before running an official unsigned installer.

The independent post-publication workflow builds standalone Support artifacts, and prepares a ZIP of the published Nodus runtime only after repair qualification. `support-release.mjs --publish` refuses recovery-artifact publication until all four gated operations are qualified for that platform and the private key matches a pinned public key. No publication has been performed by this implementation task.

The new native CI matrix covers Windows x64, macOS arm64/x64 and Linux x64; it builds all three Linux formats, runs unit tests including a real file larger than 4 GiB, captures the 12 languages in both themes, checks early bootstrap, and launches the independent packaged runtime. Native Windows/Linux/Intel execution has not been observed locally.

Before enabling a repair, record and review actual native evidence for:

1. Full SQLite/WAL recovery and schema compatibility, corrupt databases and encrypted archives, correct and incorrect passwords, damaged registries, external paths, symlinks and Windows junctions.
2. Interruption at every binary and policy transition; disk-full, permission-denied and locked-file failures; cancelled elevation; source changes during a copy; preservation and explicit selection of divergent recovered work.
3. Full-application isolation including Node networking, subprocesses, provider calls, credentials, plugin execution, backups and cleanup. The normal interactive application is intentionally gated until this is proved.
4. Real reinstall/rollback for NSIS, signed macOS bundles, AppImage, DEB and RPM; damaged installations and interrupted downloads; restoration after assistant shutdown; same-version first and explicitly approved compatible-version fallback.
5. Both user modes from symptom through confirmation and fallback report, accessible keyboard/screen-reader interaction, high contrast, scaling and reduced motion, all 12 translations and both themes.

Current local evidence: renderer/Electron/Support typechecks and targeted lint pass; protection/privacy/transaction/release tests pass, including real file streaming beyond 4 GiB in the initial verification. The Support unit tests pass locally, including real file streaming beyond 4 GiB. The real Electron UI passes 24 locale/theme screenshots and 24 automated WCAG checks, plus keyboard interaction, reduced motion and 200% scaling. Additional tests exercise the production renderer and preload with a controlled main service: both modes, failed solutions, divergent edits, report review, stopping between steps and reinstall confirmation. That UI simulation is not evidence of native installer qualification. The real independent main process also opens with damaged history/selection, blocks changes and offers a report. The independent macOS arm64 package and early bootstrap probes launch. Native SQLite compilation works with the installed macOS 26.5 SDK. The expanded native data suite now verifies committed WAL rows, external libraries, copied configuration and sync changes, plugin preservation, real library reconstruction, partial table recovery, an encrypted archive restored into an empty profile, an incorrect password, and the complete application running on copied data with networking denied. Source hashes remain unchanged. Native evidence is saved with a digest of the tested source in `.ci/support-native/`.

The desktop does **not** currently have production qualification for every repair or installer format. `qualified-repairs.json` remains empty until the complete matrix above is executed and reviewed on each platform. Neither passing the worker canvas check nor generating an installer is sufficient to fill it. Initial CI on this PR has passed the expanded data/UI/package suites on Linux x64 (AppImage, DEB and RPM), macOS arm64 and macOS Intel. The subsequent native run at `3f377729` also passed Windows x64 after fixing path boundaries, inherited runtime environment flags and durable worker outcomes. See [PR #1217 checks](https://github.com/jorgepb96/nodus/pull/1217/checks) for the results of each revision. Each new source revision must pass the matrix again. Public release remains blocked. Known automatic repair coverage is limited to the explicit catalog; vendor downloads and OS/driver work currently open official instructions. Unknown tool/provider failures produce a report.
